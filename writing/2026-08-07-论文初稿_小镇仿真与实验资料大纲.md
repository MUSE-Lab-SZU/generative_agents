# 小镇仿真与实验部分资料大纲（论文初稿交接版）

> 基于当前项目说明文档、默认配置、实验入口和核心运行模块整理。本文只覆盖 Stanford Generative Agents 小镇仿真、患者 Agent、干预流程、实验设计与评估；历史结果仅作为背景，不作为本文推荐的实验设计依据。

总体流程可概括为：

`人设/严重度配置 + 实验组 overlay → 小镇步进仿真 → 日常行为与条件化互动 → 动态抑郁状态/记忆更新 → 冻结 checkpoint → 延迟重复量表复评与过程分析`

## 2. Methods

### 2.1 Simulation Environment

#### 2.1.1 小镇环境、时间推进与运行循环

- **这一节应该写什么：** 系统基于 Stanford Generative Agents 式小镇框架扩展；地图、地点层级、角色位置与虚拟时钟共同构成环境。一次仿真按离散 step 推进：每步先调度干预/居民互动，再让各 Agent 感知、计划、行动和对话；典型批量设置为 120 step、每步 12 小时，即约 60 个虚拟日。
- **当前项目中可作为依据的文件/模块：** `start.py`、`modules/game.py`、`data/config.json`、`docs/KBD重复实验设计与结果说明_0718.md`。
- **目前信息是否充分：** **基本充分。** 论文应以实际批次的 runtime config 为准，不应把默认配置直接当作所有实验的参数。

#### 2.1.2 Agent 通用架构：感知、计划、行动与自然对话

- **这一节应该写什么：** 每个 Agent 具备空间感知、日程规划、行动分解、位置选择、关系相关记忆检索和对话生成能力。非强制互动由环境中的相遇、感知和聊天决策触发；强制互动则由实验规则优先触发。
- **当前项目中可作为依据的文件/模块：** `modules/agent.py`、`modules/game.py`、`docs/小镇全流程梳理_20260603.md`。
- **目前信息是否充分：** **充分。** 建议写机制层，不需要罗列提示词模板或函数名称。

#### 2.1.3 规则与 LLM 的分工

- **这一节应该写什么：** 强调这是“规则编排 + LLM 生成”的混合系统：规则负责时间步进、地图/路径、会面调度、实验条件、会谈推进和快照触发；LLM 负责日程、语言互动、反思、情绪推断和部分会谈判断。该表述有助于避免将系统误写成完全自主或完全确定性的仿真。

#### 2.2.2 本地记忆、检索与反思机制

- **这一节应该写什么：** 将记忆描述为 event、chat、thought 三类可检索语义记录；检索综合考虑时间新近性、语义相关性和重要性。对话和高重要性事件可进一步触发反思，形成新的 thought，从而影响后续计划与互动。

#### 2.3.2 动态抑郁状态：主诉图、情绪与提示词注入

- **这一节应该写什么：** 抑郁不是在仿真中由单一分数直接更新，而是通过结构化叙事状态体现：当前主诉节点、核心信念、触发/维持信号、关系修饰、情绪向量和互动历史。对话前系统读取当前节点并生成动态行为约束；对话或反思后提交事件，决定主诉维持或推进。
- **当前项目中可作为依据的文件/模块：** `modules/depression/engine.py`、`modules/depression/state_machine.py`、`modules/agent.py`。

#### 2.3.3 抑郁人设与小镇经历的耦合

- **这一节应该写什么：** 解释压力源如何进入小镇生活：例如 KBD2 的社会比较、回避被看见、睡眠/食欲/精力下降等，既写入初始记忆，也通过地点、关系和对话上下文影响日常行为与发言。不同 KBD 人设共享抑郁状态框架但具有不同压力叙事，可用于考察人设异质性。

### 2.4 Interaction and Intervention Mechanisms

#### 2.4.1 条件化互动的触发与会谈推进

- **这一节应该写什么：** 干预管理器可按步数、相位、角色组合和会谈类型调度互动，并为互动双方设置 lock，使患者/医生或患者/居民在该步优先完成指定对话。会后系统保存对话、聊天记忆、反思和干预运行状态。
- **当前项目中可作为依据的文件/模块：** `modules/intervention_manager.py`、`modules/resident_chat_scheduler.py`、`data/config.json`。
- **目前信息是否充分：** **充分。** 实验报告应以“实际完成互动次数/轮数”作为剂量指标，不以配置中的 duration 代替对话长度。

#### 2.4.2 G1：结构化 CBT 医患干预流程

- **这一节应该写什么：** G1 包含定期医生—患者会谈、10 个顺序化 CBT 阶段提示、会前/会中对话判断、会后 session 评估、咨询历史和可选环境任务。内容覆盖信息收集与认知三角、认知概念化、核心信念、低门槛行为实验与复盘、工具盘点、心理急救和结束。
- **当前项目中可作为依据的文件/模块：** `data/prompts/intervention_prompts.json`、`experiments/config/groups/g1_doctor_intervention.json`、`docs/cbt_refactor/01_current_flow.md`。
- **目前信息是否充分：** **基本充分。** 需准确写成：完整 session prompt 主要供 Judge 与会后评估使用，医生回复接收的是 Judge 形成的建议及记忆/对话上下文，不能简单声称“完整 CBT prompt 直接注入医生每一句回复”。

#### 2.4.3 G1 的会谈内外控制逻辑

- **这一节应该写什么：** 每轮患者发言后，Judge 综合患者动态状态、当前 CBT 阶段、既往会后原因和本场对话，为医生给出回应建议及本场是否收束的判断。整场对话结束后，session evaluator 决定是否推进到下一 CBT 阶段；当前 legacy 流程按固定顺序线性推进。
- **当前项目中可作为依据的文件/模块：** `docs/cbt_refactor/01_current_flow.md`、`modules/intervention_manager.py`、`modules/session_prompt_injection_manager.py`。
- **目前信息是否充分：** **充分。** 但若目标实验使用 `progressive` 控制器，则必须另写其 Progressive D 状态追踪与子目标评估，不能沿用本段 legacy 说明。

#### 2.4.4 医生、居民与主动比较条件

- **这一节应该写什么：** 医生 Agent 在 G1 中实施结构化 CBT；G6 为同频率的支持性咨询，强调理解、接纳和情绪验证，不推进 CBT 阶段；G3/G5/G9 分别提供中性、负向/无效支持、积极的居民聊天，并使用相同居民候选池与相近的调度频率。
- **当前项目中可作为依据的文件/模块：** `experiments/config/groups/g3_random_resident_chat.json`、`experiments/config/groups/g5_negative_resident_chat.json`、`experiments/config/groups/g6_supportive_counseling.json`、`experiments/config/groups/g9_positive_resident_chat.json`。
- **目前信息是否充分：** **充分。** 应明确 G6 是主动治疗比较，而不是无干预对照；G3/G5/G9 也不是去除了所有系统机制的极简对照。

### 2.5 Experimental Design

#### 2.5.1 实验因素、组别与对照逻辑

### 2.6 Outcome Evaluation and Analysis

#### 2.6.1 冻结状态与后续量表复评

- **这一节应该写什么：** 仿真进行到 T0 和各阶段节点时，系统会保存当时完整的患者状态、记忆和运行时上下文；量表不在仿真过程中立即作答，而是在仿真完成后从这些已保存状态中分别恢复并评估。这样可避免量表问答改变原始仿真轨迹，也能对同一状态重复评估。
- **当前项目中可作为依据的文件/模块：** `data/config.json`、`modules/staged_eval_manager.py`、`README_counsel_room.md`。
- **目前信息是否充分：** **充分。** 这是方法部分必须交代的关键点；应避免表述为“量表在仿真每个时间点实时测得”。

#### 2.6.2 PHQ-9 与 BDI-II 的回答、评分与校验流程

- **这一节应该写什么：** 冻结状态下由患者 Agent 逐项生成自评量表回答，再由独立评分流程得到条目分和总分；主线使用 PHQ-9（0–27）和 BDI-II（0–63）。规则评分后还会进行校验：逐条核对患者回答中是否明确表达“几分/第几项”，若存在明确分值线索，则用于核对或修正条目级分数；最终总分以校验后的条目分汇总。该设计与两份量表均为自评量表的性质一致。
- **当前项目中可作为依据的文件/模块：** `runshells/run_scale_worker.py`、`runshells/run_score_worker.py`、`customization/depression_scale_agent/app.py`、`runshells/validate_scale_score_results.py`。
- **目前信息是否充分：** **基本充分。** 应如实称为“LLM 模拟患者自评 + LLM/规则评分与回答一致性校验”，而非真实临床量表施测。

#### 2.6.3 重复复评、可靠性和主要结局（调研中）
